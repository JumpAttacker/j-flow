# Бриф исполнителя

Контроллер передаёт этот шаблон `j-implementer` для задачи или раунда исправлений.
Политика процесса задана в [SKILL.md](../SKILL.md); правила проекта и поручение
пользователя определяют разрешённые действия.

## Вход

- `[BRIEF_FILE]`: точный текст задачи; прочитай первым.
- `[PROJECT_RULES]`, `[WORKDIR]`, `[OWNED_PATHS]`: правила, каталог, разрешённые файлы.
- `[CONSTRAINTS_AND_INTERFACES]`: обязательные ограничения, точные контракты зависимостей,
  решения контроллера и известные чужие изменения.
- `[TEST_POLICY]`, `[COMMIT_PERMISSION]`: проверки по задаче и полномочия на коммит.
- `[REPORT_FILE]`: полный результат; при правках дописывай, не затирай прошлые раунды.
- `[FINDINGS]`: открытые замечания, только для раунда исправлений.

## Работа

1. Проверь вход и доступность зависимостей. Недостающие требования верни контроллеру
   как `NEEDS_CONTEXT`; невозможность продолжить с доступными средствами как `BLOCKED`.
   Рутинные решения принимай в пределах задачи; изменение согласованного интерфейса
   или области работы сначала передай контроллеру.
2. Выполни задачу по существующим паттернам проекта. Чужие изменения сохраняй.
   Дополнительных агентов и собственного ревьюера не вызывай.
3. Применяй [test-driven-development.md](test-driven-development.md) при изменении
   проверяемого поведения, учитывая проектную политику. Разработка unit/integration
   проверок и отдельная методология QA E2E имеют разные области и исполнителей.
4. При итерациях запускай проверки затронутого поведения. Обязательные проектные
   проверки выполни до отчёта; неизменённые проверки не повторяй без причины.
5. Самостоятельно прочитай свой diff: полнота брифа, ошибки и границы, отсутствие
   лишней реализации, полезность тестов, сохранение чужой работы.
6. Коммит только при разрешении и только своих путей. Незакоммиченные правки допустимы.
   Завершай лишь собственные процессы по PID, запиши очистку в отчёт.

## Полный отчёт

В `[REPORT_FILE]` запиши статус, реализованное поведение, изменённые файлы, состояние
кода (SHA либо рабочее дерево с путями/патчем), команды проверок, коды выхода и
значимый вывод. Для TDD укажи ожидаемое падение до реализации и успех после неё.
Добавь результат самопроверки, отклонения, сомнения и оставшиеся ограничения.
Для раунда правок свяжи каждое замечание с изменением и покрывающей проверкой.
Если запись отчёта недоступна, верни его текстом без обхода ограничения.

В коротком ответе: `DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED`, путь отчёта,
коммиты либо «без коммита», одна строка проверок, существенные сомнения.
При `NEEDS_CONTEXT`/`BLOCKED` сразу назови нужный вход или препятствие.
