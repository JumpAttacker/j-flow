# План исполнения

## Когда читать

Контроллер читает после согласования архитектурного решения, до исполнения.
Разрешения, политика тестирования и порядок гейта заданы в [SKILL.md](../SKILL.md).
Небольшая bounded-задача не требует такого плана.

## Границы и размер задач

План сохраняется в `.j-flow/plans/YYYY-MM-DD-<topic>.md` или в место из правил проекта.
Сначала определи изменяемые модули, ответственность файлов и интерфейсы между ними.
Одна задача даёт самостоятельный проверяемый результат. Подготовку, конфигурацию
и документацию включай в задачу, которой они нужны; отдельные шаги TDD не делай
отдельными задачами плана.

Исполнитель видит одну задачу, поэтому выпиши точные входы и выходы между задачами:
имена, сигнатуры, форматы данных, совместимость и обязательные ограничения.
Конкретные значения из решения передавай дословно. Детали реализации оставляй
исполнителю, если они не определяют контракт или проверяемое поведение.
Полную будущую реализацию и код каждого теста заранее писать не требуется.

## Формат

Заголовки `### Task N:` используются помощником `task-brief`; текст задачи может
быть на языке служебного плана. Номер и название не должны находиться внутри code fence.

```markdown
# План: <задача>

## Решение и приёмка
Ссылка на согласованное решение, наблюдаемый результат и критерии готовности.

## Global Constraints
Рабочие зоны и владение файлами, запреты и разрешения проекта.
Применимая политика тестирования, команды и доступные проверки.
Точные значения, интерфейсы, совместимость и возможность коммита.

### Task 1: <самостоятельный результат>
Результат: что изменится для пользователя или вызывающего кода.
Файлы: создаваемые, изменяемые и проверяемые пути.
Зависимости: нужные результаты предыдущих задач.
Входы/выходы: точные контракты для соседних задач.
Ограничения: применимые требования и разрешения из Global Constraints.
Проверка: сценарии, команды, ожидаемые исходы и место доказательств.
- [ ] Реализовать результат с проверками по политике проекта.
- [ ] Выполнить названные проверки и сохранить отчёт.
- [ ] Передать изменение для ревью; коммит только при разрешении.
```

Для TDD называй проверку отсутствующего поведения. Ошибка запуска, опечатка или
сломанный setup не является доказательством этого поведения. Если язык требует
сначала объявить интерфейс для компиляции, отдели минимальный каркас от реализации
и проверь поведение после успешного запуска теста.

## Проверка плана

Контроллер сверяет покрытие приёмки, порядок зависимостей, согласованность интерфейсов
и достаточность брифов. Неизвестные контрактные решения разреши до зависимой задачи;
не добавляй спекулятивные подсистемы ради возможного будущего применения.
Затем передай план и согласованное решение `j-critic` по
[plan-document-reviewer-prompt.md](plan-document-reviewer-prompt.md).
В режиме без делегирования выполни ту же проверку сам, указав отсутствие независимого ревью.

Исправь подтверждённые дефекты плана. Если исправление существенно меняет согласованное
решение, обсуди изменение с владельцем; уточнение деталей не создаёт повторного гейта.
После проверки продолжай в текущей сессии по
[subagent-driven-development.md](subagent-driven-development.md).
