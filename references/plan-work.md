# Спланировать работу

После одобрения архитектурной задачи контроллер готовит план по текущему описанию,
согласованным требованиям и способам проверки. Если короткая задача обходится без полного
плана, достаточно брифа и приёмки. Разрешения берутся из SKILL.md и проекта.

Сначала опиши изменяемую ответственность: кто вызывает модуль, что передаёт и получает,
какие ошибки возможны и какие зависимости нужны. Дополнительный слой полезен, когда
упрощает использование или локализует изменение; причину его появления назови конкретно.

Разбей результат на части, которые можно проверить по поведению. Для пользовательской
функции предпочитай маленький работающий путь через нужные слои. Массовый перенос
или переименование разбивай по совместимости: новая форма, переход потребителей, удаление старой.

Для каждой `### Task N: ...` укажи результат, интерфейсы, файлы владения, зависимости,
проверку и ограничения. Зависимость задаётся необходимым результатом другой задачи;
общие файлы и один runtime требуют последовательности. Перечень свободных задач
определяется завершёнными зависимостями и разрешением на параллельную работу.

План содержит общие ограничения и критерии завершения целого. Критик проверяет план
по [review-plan.md](review-plan.md), исполнитель получает только нужную задачу и контракты.
Публикация задач в трекер возможна только при отдельной авторизации проекта.
