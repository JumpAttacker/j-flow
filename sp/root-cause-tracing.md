# Поиск источника неверного значения

## Когда читать

Читай из [systematic-debugging.md](systematic-debugging.md), когда ошибка возникает
глубоко в цепочке вызовов или неизвестно, откуда пришёл неверный вход. Общие правила
и область разрешённой работы задаёт [SKILL.md](../SKILL.md).

## Обратное прослеживание

Найди операцию, в которой проявился сбой, и её фактический вход. Затем переходи
к вызывающему коду: кто передал это значение, как оно было получено и когда впервые
стало неверным. Проверяй преобразования, значения по умолчанию, порядок инициализации
и чтение общего состояния. Остановись на подтверждённом источнике, который объясняет
весь путь до симптома.

Пример: команда Git создала репозиторий в исходниках. Проверка аргумента рабочего
каталога показала пустую строку. Прослеживание вызовов обнаружило, что тест прочитал
временный каталог до подготовки окружения. Исправление относится к инициализации
тестовых данных; ловля ошибки Git сама по себе не устраняет источник.

Если стек недостаточен, добавь временную диагностику перед подозрительной операцией:
безопасные параметры, идентификатор сценария, порядок вызовов и стек. Используй
канал, который действительно сохраняется в выводе тестов. Не выгружай секреты
и весь environment. Сопоставь наблюдения с конкретным запуском, затем убери лишнюю
диагностику.

## Поиск теста, загрязняющего окружение

Используй реальный runner проекта и его способы выбора тестов, без универсальной
предполагаемой команды.

1. В изолированном окружении зафиксируй исходное состояние подозрительного файла,
   каталога или ресурса. Если загрязнение уже есть, сначала получи чистую исходную
   копию; не удаляй неизвестные файлы рабочего проекта.
2. Получи список выбранных тестов средствами runner. Пустой список и ошибка runner
   означают непроверенный запуск, а не чистое окружение.
3. Запускай группы с восстановлением исходного состояния между экспериментами.
   Сохраняй вывод и код завершения, проверяй состояние ресурса после запуска.
   Сбой теста не отменяет наблюдение загрязнения, но не позволяет объявить группу
   успешно проверенной. Ошибка подготовки или runner может сделать вывод неясным.
4. Уменьшай воспроизводящую группу делением пополам. Если обе части чистые,
   проверь их взаимодействие, порядок и параллельное исполнение: виновник может
   проявляться только после другого теста или при конкуренции.
5. Подтверди минимальный сценарий, проследи источник записи или изменения состояния
   и исправь владение ресурсом, подготовку либо очистку.

После подтверждения источника добавляй дополнительные проверки только для независимых
опасных границ по [defense-in-depth.md](defense-in-depth.md).
