# Исполнить план с журналом

Контроллер читает план и общие ограничения, проверяет зависимости и исходную работу.
При наличии Git и исходного коммита из корня выбранного проекта получает каталог:
`node "<skill-root>/scripts/sdd-workspace.mjs" PLAN`. Корнем разрешённых путей является
этот проект, даже если Git-репозиторий общий с соседними проектами.
Журнал начинается `# SDD ledger: plan: <путь плана от корня>` и хранит исходный BASE,
режим исполнения, задачи, раунды, ограничения, источники и следующий шаг.
Повторный запуск сверяет план с журналом и файлами; завершённая задача не исполняется заново.
Утилита продолжает единственный журнал с подтверждённой идентичностью этого плана;
несколько подходящих журналов требуют явного выбора контроллера до записи.

Если Git отсутствует или в нём ещё нет исходного коммита, используй тот же журнал
в отдельном каталоге плана без Git-помощников. Зафиксируй идентичность плана,
исходные файлы и их хеши/копии, точный текст задачи и версии до/после каждого раунда.
Коммит или инициализация Git ради процедуры не требуются; они подчиняются разрешениям проекта.

## Передача задачи

`node "<skill-root>/scripts/task-brief.mjs" PLAN N` извлекает бриф задачи.
Исполнитель получает рабочий каталог, владение файлами, интерфейсы зависимостей,
применимую тестовую политику, разрешения и путь результата. Прочие задачи и полная
история не заменяют этих входов. Общие файлы и один runtime исполняются последовательно.

После DONE контроллер собирает пакет для ревью:

```bash
node "<skill-root>/scripts/review-package.mjs" PLAN BASE HEAD
node "<skill-root>/scripts/review-package.mjs" PLAN BASE --working-tree -- PATH...
```

Второй режим охватывает только названные пути, включая новые и удалённые файлы.
Без Git/BASE пакет составляется из сохранённых версий принадлежащих задаче файлов:
изменения, добавления и удаления с именами и доступными доказательствами.
Чужую работу внутри общего файла отдели сохранённой исходной копией или явно назови
ограничение пакета. Ревьюер получает бриф, отчёт, границы изменений и правила.
NEEDS_CONTEXT означает передачу отсутствующего входа; BLOCKED требует изменения подхода,
а не повторения той же попытки. Сомнения исполнителя разбираются до завершения задачи.

## Замечания и фиксация

Требования и существенные дефекты проходят исправление и [review-fixes.md](review-fixes.md).
Перед раундом сохрани проверенную версию; ревью получает разницу именно этого раунда.
Первые три раунда ведёт исходный исполнитель, четвёртый и пятый новый с полной передачей.
После пяти раундов контроллер разбирает остаток и решение с риском; лимит не закрывает дефект.
Небольшой допустимый долг записывается и попадает в итоговое ревью.

Задача завершена после проверки требований и разрешения замечаний. Запиши отчёт, ревью,
состояние файлов и следующий шаг в журнал и state. Изменения устройства передаются хранителю.
После задач критик проверяет интеграцию по [review-integration.md](review-integration.md).
При остановке также сохраняются документы и ограничения. Без делегирования контроллер
выполняет отдельные проходы сам и честно сообщает отсутствие независимого ревью.
