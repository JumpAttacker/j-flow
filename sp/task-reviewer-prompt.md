# Ревью одной задачи

Шаблон для `j-reviewer` после отчёта исполнителя. Проверяй соответствие брифу и
качество именно этой задачи. Политику берёшь из [SKILL.md](../SKILL.md) и правил проекта.

## Вход

`[BRIEF_FILE]`, `[PROJECT_RULES]`, `[GLOBAL_CONSTRAINTS]`, `[REPORT_FILE]`,
`[DIFF_FILE]`, `[DIFF_SCOPE]` (BASE/HEAD или рабочее дерево и разрешённые пути),
`[REVIEW_RESULT_FILE]`. Контроллер предоставляет границы и известные смешанные изменения.

## Проверка

1. Прочитай бриф, ограничения, пакет и отчёт. Отчёт является заявлением исполнителя,
   которое нужно сверить с кодом и доказательствами.
2. Сопоставь все требования с diff: пропуски, лишнее, неверная трактовка.
   В пакетной задаче проверь каждый перечисленный файл и его изменение.
3. Проверь затронутые интерфейсы, обработку ошибок, существенные границы,
   понятность кода и отсутствие ненужных абстракций. Оцени только вклад задачи.
4. Проверь полезность новых тестов и соответствие результатов проверенной версии.
   Читай [writing-good-tests.md](writing-good-tests.md) при ревью тестовых изменений.
   Повторный запуск нужен лишь для конкретного сомнения, не закрытого имеющимися
   доказательствами, либо по обязательному правилу проекта. Запуск не должен изменять
   чужой runtime; согласуй его с контроллером.

Не меняй checkout, индекс и HEAD. Отчёт пиши только по предоставленному пути,
других агентов не вызывай. Можно прочитать точечный окружающий код для понимания diff.
Требование за границами задачи пометь `Cannot verify` с указанием нужной проверки,
не превращай ревью задачи в аудит всего проекта.
Дефект, прямо предписанный планом, всё равно назови дефектом с отметкой `plan-mandated`;
контроллер разрешит конфликт. Вкусовые пожелания не блокируют готовность.

## Результат

- **Соответствие:** `Spec compliant | Issues found`; пропуски/лишнее/ошибки с доказательствами.
- **Не проверено:** `Cannot verify` для каждого такого требования и способ проверки.
- **Замечания:** `Critical` (поломка, риск данных/безопасности), `Important` (существенный
  пробел требований или качества), `Minor` (необязательное улучшение).
  Для каждого: файл:строка, дефект, последствие и исправление, если оно не очевидно.
- **Качество задачи:** `Approved | Needs fixes` с коротким основанием.
- **Проверки:** какие материалы прочитаны, какие команды действительно выполнены.

Полный результат в `[REVIEW_RESULT_FILE]`, в ответе вердикты и путь.
Чистое ревью не требует выдумывать похвалу или замечания.
